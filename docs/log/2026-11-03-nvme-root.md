# Root filesystem on NVMe (SD card keeps /boot)

## TL;DR
Moving `/` from the SD card to an M.2 NVMe SSD makes the disk about 16x faster
for small random reads and writes, but the board does not feel faster. Boot
time is the same, and launching SEB showed no noticeable difference. It also
needs a kernel flag to work around a JH7110 PCIe bug. Not recommended for the
project. The board is CPU-bound (see
`2026-09-30-GPU-and-current-state-of-peformance.md`), so effort is better spent
on software and firmware; see "Where to look instead".

## Setup
| Item | Value |
|---|---|
| Board | Orange Pi RV (StarFive JH7110), `orangepi-000595` |
| OS | Vendor Debian, kernel `5.15.0-starfive2` |
| SD card | 64 GB microSD, `mmcblk1` |
| SSD | 250 GB NVMe in the M.2 slot, PCIe 2.0 x1 (about 4 Gb/s max) |

The board loads the kernel from the SD card's `/boot`, so the SD card stays in.
Only `/` moves to the SSD. The kernel has NVMe and PCIe built in
(`CONFIG_BLK_DEV_NVME=y`), so the initrd needs nothing extra.

## Moving / to the SSD
This erases the SSD.

```bash
sudo wipefs -a /dev/nvme0n1
sudo parted -s /dev/nvme0n1 mklabel gpt mkpart ssd_root ext4 1MiB 100%
sudo mkfs.ext4 -L ssd_root /dev/nvme0n1p1
sudo mkdir -p /mnt/ssd
sudo mount /dev/nvme0n1p1 /mnt/ssd
sudo rsync -aAXHx --info=progress2 / /mnt/ssd/
```

`-x` copies only the root filesystem and skips `/boot`, `/proc`, `/tmp` and
other mounts. Then point the SSD's fstab and the SD card's boot config at the
SSD (`OLD` is the root UUID from `cat /proc/cmdline`):

```bash
OLD=<current root UUID>
NEW=$(sudo blkid -s UUID -o value /dev/nvme0n1p1)
sudo sed -i "s/$OLD/$NEW/" /mnt/ssd/etc/fstab
sudo cp /boot/extlinux/extlinux.conf /boot/extlinux/extlinux.conf.sd
sudo sed -i "s/root=UUID=$OLD/root=UUID=$NEW/" /boot/extlinux/extlinux.conf
```

Add the NVMe timeout workaround (see below) to the same boot line, then reboot:

```bash
sudo sed -i '/append root=/ s/$/ nvme_core.io_timeout=2/' /boot/extlinux/extlinux.conf
sudo umount /mnt/ssd
sudo reboot
```

Check with `findmnt /`, which should show `/dev/nvme0n1p1`.

Rollback: on a laptop, copy `extlinux/extlinux.conf.sd` over
`extlinux/extlinux.conf` on the SD card's boot partition. The old root
partition on the SD card is left untouched, so the board boots exactly as
before.

## How it was measured
`scripts/bench-board.sh`, right after a reboot:

```bash
./scripts/bench-board.sh --host orangepi@10.0.0.40 --label sd
```

It records boot time (`systemd-analyze`), 4k random read/write (fio, queue
depth 1, `--direct=1`, 30s), a cold read of many small files (`ls -R /usr`
after dropping the page cache), and any NVMe timeouts, and saves the result
under `cache/bench/`.

## Results
| | SD card | NVMe | NVMe + `io_timeout=2` |
|---|---|---|---|
| 4k random read IOPS | 366 | 5,799 | 5,754 |
| 4k random write IOPS | 364 | 5,789 | 5,748 |
| avg read latency | 673 µs | 93 µs | 94 µs |
| avg write latency | 2,035 µs | 64 µs | 66 µs |
| boot, kernel | 21.8 s | 51.1 s | 23.3 s |
| boot, userspace | 44.3 s | 67.0 s | 37.8 s |
| boot, total | 1 min 6 s | 1 min 58 s | 1 min 1 s |
| cold `ls -R /usr` | 5.3 s | 17.8 s | 2.5 s |

The SD card was at 99.8% utilization for the whole fio run. One board, one run
per setup.

## NVMe timeouts on JH7110
Without the workaround, the SSD was slower than the SD card at boot. `dmesg`
showed:

```
[42.18] nvme nvme0: I/O 126 QID 3 timeout, aborting
[51.04] EXT4-fs (nvme0n1p1): mounted filesystem ...
[81.86] nvme nvme0: I/O 106 QID 3 timeout, completion polled
```

The SSD was ready at 5 s, but `/` only mounted at 51 s. This is a known
JH7110 PCIe bug that StarFive described on the kernel mailing list: sometimes
the SSD's completion isn't visible yet when its interrupt arrives, so the
kernel misses it and waits out the 30 s I/O timeout before polling. Their fix
is not in this 5.15 kernel.

`nvme_core.io_timeout=2` cuts each miss from 30 s to about 2 s. It still
happens (one miss at 14 s on the measured boot), but it no longer matters. A
newer kernel with StarFive's fix would remove it.

## Verdict
Not recommended. The disk is much faster on paper, but nothing a student or
proctor sees gets noticeably faster:

- Boot time is the same as the SD card (1 min 1 s vs 1 min 6 s).
- A quick side-by-side SEB launch on the same board showed no noticeable
  difference.
- Exam-time slowness is the CPU running Canvas's JavaScript on one core. A
  faster disk does not touch that.

And it costs something: an SSD per board, a manual move, a second storage
device to fail (SD still holds `/boot`), and a workaround for a kernel bug.

Where it does help is disk-heavy work: apt, installs, and building on a board
(`build-seb.sh`). Fine for a personal build board, not worth rolling out.

## Where to look instead
Ideas to check, roughly in order of expected payoff:

- **JavaScript engine.** Canvas is JavaScript-bound, so check whether
  JavaScriptCore's JIT is active in the board's WebKitGTK 2.38.2 build. Time a
  JS-heavy page with and without `JSC_useJIT=false`; if there's no difference,
  JS is running in the interpreter, which is many times slower. Newer
  WebKitGTK releases build the JIT on riscv64, so a WebKit upgrade could be
  the biggest single win.
- **CPU clock and heat.** Confirm the cores actually run at 1.5 GHz during an
  exam and the governor isn't holding them back
  (`/sys/devices/system/cpu/cpu*/cpufreq/scaling_governor`,
  `scaling_cur_freq`). The GPU log saw ~75°C, so check for thermal
  throttling and consider a heatsink or fan.
- **Trim the image.** Boards run SEB in a kiosk, but still boot the full
  desktop: `plymouth-quit-wait` alone takes ~23 s of boot, and services like
  `blueman` aren't needed. Turning off what the kiosk doesn't use frees CPU
  and RAM and shortens boot.
- **Kernel and firmware.** A newer kernel with upstream JH7110 support would
  bring driver fixes (including StarFive's NVMe fix) and scheduler and power
  improvements. This is the largest change and needs the GPU stack ported to
  it.

`scripts/bench-board.sh` covers boot time and disk; a SEB or Canvas timing
test would be the next thing to add before and after any of these.
